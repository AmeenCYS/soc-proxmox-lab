PHASE 01

Preflight Before Touching the Server

Safety: Have local console, iDRAC, or iLO access before changing Proxmox networking. A wrong bridge or gateway can disconnect the host.

Practical host

  • 128 GB RAM practical minimum; 160–192 GB preferred.
  • 2 TB NVMe minimum; 3–4 TB or separate PCAP disk preferred.
  • One NIC works for a virtual lab; two or more improve separation.
  • Enable Intel VT-x/VT-d or AMD-V/IOMMU.

Project records

  • Record the Proxmox node, management IP, and gateway.
  • Create a dedicated password-manager vault.
  • Assign an owner and install date to every service.
  • Never put secrets or tokens in GitHub.

PHASE 03

Install and Baseline Proxmox VE

  1. Write the ISO to USB, boot the physical server, and select Install Proxmox VE.
  2. Choose the OS disk carefully. Keep a separate PCAP disk unused if available.
  3. Set location, time zone, keyboard, administrative email, and a strong password.
  4. Choose the management NIC and set pve01.corp.lab, 192.168.1.10/24, gateway 192.168.1.1, and a temporary working DNS server.
  5. Open https://192.168.1.10:8006 from a trusted LAN and sign in.
  6. Configure NTP, inspect storage, and patch from the repository appropriate for your subscription.
  7. Enable MFA and create a named administrator instead of using root daily.
pveversion -v
ip -br address
ip route
timedatectl
lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS
Use the current Proxmox repository documentation. Do not enable both enterprise and no-subscription repositories for the same packages.
Success gate: The UI returns after reboot and package status is healthy.
PHASE 04

Create the Virtual Bridges

vmbr0

External/OOB: Proxmox management, pfSense WAN, and NB-GW01.

vmbr1

No-IP VLAN-aware internal trunk for zones 10–60.

vmbr2

No-IP monitoring bridge that feeds the SO01 sniff NIC.

How to read it: the router, Proxmox management, pfSense WAN, and NB-GW01 are peers on the same Layer 2 vmbr0 segment—not a routed chain through the Proxmox management IP. VLAN 10 is the Admin Jumpbox source zone; PVE itself remains on OOB in this lab design.

Prefer Node → System → Network. Replace eno1 with the real interface from ip -br link.

auto lo
iface lo inet loopback

iface eno1 inet manual

auto vmbr0
iface vmbr0 inet static
    address 192.168.1.10/24
    gateway 192.168.1.1
    bridge-ports eno1
    bridge-stp off
    bridge-fd 0

auto vmbr1
iface vmbr1 inet manual
    bridge-ports none
    bridge-stp off
    bridge-fd 0
    bridge-vlan-aware yes
    bridge-vids 10 20 30 40 50 60

auto vmbr2
iface vmbr2 inet manual
    bridge-ports none
    bridge-stp off
    bridge-fd 0
Apply from a local console. Do not run a remote network reload without a recovery path.
Success gate: Proxmox remains reachable and vmbr1/vmbr2 have no IP or gateway.

PHASE 06

Create VLANs, DHCP, and Firewall Policy

  1. Create VLANs 10, 20, 30, 40, 50, and 60 on parent vtnet1.
  2. Assign and enable interfaces named MGMT, USERS, SERVERS, SOC, DMZ, and ATTACK.
  3. Give them 10.10.X.1/24; do not set upstream gateways on internal interfaces.
  4. Enable DHCP on USERS (10.10.20.100–200) and ATTACK (10.10.60.100–150) only. Servers use static IPs.
  5. Create aliases for DC01, SOC_SERVERS, DMZ_SERVERS, and management ports.
  6. Order rules from most specific to least specific and log final denies.

PHASE 11

Deploy Security Onion Network Visibility

  1. Create SO01 with host CPU, 24 GB RAM, 300 GB disk, management NIC on tag 40, and a second no-tag NIC on vmbr2.
  2. Boot the official ISO and choose a Standalone lab deployment.
  3. Set management IP 10.10.40.20/24, gateway 10.10.40.1, and DNS 10.10.30.10.
  4. Assign the second NIC as monitor/sniff only, with no IP or gateway.
  5. Allow management only from MGMT/NetBird.
  6. Start with one mirror source: the pfSense internal interface; add east-west sources only after validation.
  7. Monitor capture loss, Zeek loss, and storage growth.
Do not guess tap names. Proxmox interface names depend on VMID/NIC and can change. Resolve them after FW01 and SO01 are running and follow current Security Onion/Proxmox mirroring guidance. Use a physical TAP or switch SPAN in production.
Important: creating vmbr2 and attaching the sniff NIC does not mirror traffic automatically. Configure an explicit Mirror/TAP/SPAN from the pfSense internal interface or approved capture source.

PHASE 12

Deploy OpenCTI on CTI01

  1. Build CTI01 with Ubuntu 24.04, 8 vCPU, 24 GB RAM, 250 GB, and 10.10.40.40.
  2. Install Docker Engine and Compose plugin from Docker's official repository.
  3. Clone the official OpenCTI Docker repository and copy .env.sample to .env.
  4. Replace every password, create valid UUIDv4 admin/connector IDs, and a long encryption key.
  5. Persist vm.max_map_count=1048575.
  6. Start the stack, inspect health/logs, and stabilize core services before adding connectors.
  7. Start with MITRE ATT&CK and one trusted CTI source. Use a separate least-privilege token per connector.
  8. Restrict UI/API to SOC/MGMT or NetBird and add an internal TLS reverse proxy.
sudo sysctl -w vm.max_map_count=1048575
echo 'vm.max_map_count=1048575' | sudo tee /etc/sysctl.d/99-opencti.conf
git clone https://github.com/OpenCTI-Platform/docker.git ~/opencti-docker
cd ~/opencti-docker

uuidgen
openssl rand -base64 32

PHASE 13

Deploy n8n as the SOAR Layer

  1. Baseline SOAR01 at 10.10.40.30 and install Docker/Compose from official sources.
  2. Use persistent SQLite only for the lab; move to PostgreSQL for always-on or multi-user use.
  3. Generate an encryption key, set Asia/Riyadh time, and store tokens in credentials rather than workflow JSON.
  4. Restrict port 5678 to MGMT temporarily, then add TLS before NetBird access.
  5. Create separate least-privilege credentials for Wazuh, OpenCTI, and notifications.
  6. Build: Test Webhook → Normalize JSON → OpenCTI HTTP Request → Confidence IF → Notify → Manual approval.
  7. Keep block/isolate behind human approval and provide rollback.
sudo docker volume create n8n_data
sudo docker run -d --name n8n --restart unless-stopped \
  -p 10.10.40.30:5678:5678 \
  -e TZ=Asia/Riyadh \
  -e GENERIC_TIMEZONE=Asia/Riyadh \
  -e N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true \
  -v n8n_data:/home/node/.n8n \
  docker.n8n.io/n8nio/n8n:latest
sudo docker ps
curl -I http://10.10.40.30:5678
This is an internal lab baseline. Pin a version, add TLS, and back up the volume, workflows, and encrypted credentials before reliance.
Success gate: The webhook crosses all nodes without revealing a token in execution output.
PHASE 14

Configure Secure NetBird Access

The first design uses NetBird Cloud and NB-GW01 as a routing peer. No management dashboard is exposed publicly.

  1. Build NB-GW01 on vmbr0 at 192.168.1.20/24, gateway 192.168.1.1.
  2. Install the client and enroll with a short-lived dedicated setup key, then revoke that key.
  3. Add a route to 10.10.0.0/16 through pfSense WAN 192.168.1.2.
  4. Create a NetBird Network named SOC-LAB and assign NB-GW01 as routing peer.
  5. Add /32 resources for Proxmox, Wazuh, Security Onion, n8n, OpenCTI, and DC01. Avoid a broad 10.10.0.0/16 user resource.
  6. Create SOC-Admins and port-specific policies; enable MFA/SSO and activity logging.
  7. Test from a laptop on cellular Internet, then prove an unauthorized identity is denied.
curl -fsSL https://pkgs.netbird.io/install.sh | sh
read -rsp "NetBird setup key: " NETBIRD_SETUP_KEY
sudo netbird up --setup-key "$NETBIRD_SETUP_KEY"
unset NETBIRD_SETUP_KEY
sudo ip route add 10.10.0.0/16 via 192.168.1.2
netbird status
ip route get 10.10.40.10

Persist the route through Netplan only after it works. Default masquerade simplifies return routing; disabling it requires explicit return routes.

Success gate: SOC-Admins reach only approved resources; another group is denied.
PHASE 15

Connect Detection, Enrichment, and Response

Detect

Wazuh for endpoints, Security Onion for network, pfSense for policy.

Enrich

n8n extracts an IP/domain/hash and queries OpenCTI for context.

Respond

Notify/ticket, request approval, then perform scoped action with rollback.

  1. Normalize timestamp, source, host, user, rule_id, severity, observable_type, and observable_value.
  2. Use a read-only Wazuh API identity or a version-reviewed webhook integration—not admin.
  3. Create a dedicated OpenCTI service token that reads indicators and observables.
  4. In n8n, call http://10.10.40.40:8080/graphql with a stored credential and a query tested in the OpenCTI API playground.
  5. Continue the incident when no IOC is found instead of dropping the alert.
  6. Create a ticket and approval request for high-confidence trusted matches. Do not write every alert back into OpenCTI.
  7. Record analyst, decision, action time, result, and rollback in every response workflow.
Success gate: A test alert reaches n8n, queries OpenCTI, notifies, and performs no block without approval.

PHASE 17

Harden and Back Up

Hardening

  • MFA on Proxmox, NetBird, and sensitive identities.
  • Named admin accounts and RBAC.
  • No public management port forwards.
  • Default deny between zones.
  • Version pinning and monthly patch windows.
  • Revoke unused keys and tokens.

Backups

  • Proxmox configuration and VM backups.
  • DC01 System State.
  • Wazuh custom rules/configuration.
  • OpenCTI volumes, Compose, and protected secret record.
  • n8n workflows, credentials, and volume.
  • Encrypted pfSense config.xml.
  1. Create a backup schedule independent of snapshots.
  2. Keep an encrypted off-host copy with documented retention.
  3. Restore a small VM, then test service-level n8n/OpenCTI restoration.
  4. Document lab RPO/RTO and recovery-key ownership.
Success gate: One service and its data can be restored without relying on a live snapshot.
