هذا الملف هو دليل التطبيق العملي المكمل لمخطط المعمارية. نفّذ المراحل بالترتيب، ولا تنتقل للمرحلة التالية حتى تنجح بوابة التحقق. ضع علامة على كل مهمة؛ سيُحفظ تقدمك محليًا في المتصفح.

المرحلة 01

التجهيز قبل لمس السيرفر

تنبيه: احتفظ بوصول Console محلي أو iDRAC/iLO قبل تغيير شبكة Proxmox. خطأ واحد في bridge أو gateway قد يقطع الإدارة عن السيرفر.

المواصفات العملية

  • 128 GB RAM كحد عملي، و160–192 GB مفضّل.
  • 2 TB NVMe كحد أدنى، و3–4 TB أو قرص PCAP منفصل مفضّل.
  • NIC واحدة تكفي للمختبر الافتراضي؛ اثنتان أفضل للفصل.
  • فعّل Intel VT-x/VT-d أو AMD-V/IOMMU من BIOS.

سجل المشروع

  • اكتب اسم عقدة Proxmox وعنوان الإدارة والبوابة.
  • أنشئ Password Manager vault للمشروع.
  • حدد مالك كل خدمة وتاريخ تثبيتها.
  • لا تضع كلمات المرور أو tokens داخل GitHub.

المرحلة 03

تثبيت Proxmox VE وإعداد الأساس

  1. اكتب ISO على USB، أقلع السيرفر، واختر Install Proxmox VE.
  2. اختر قرص النظام بعناية. إذا عندك قرص PCAP مستقل فلا تستخدمه للنظام.
  3. اضبط الدولة والمنطقة الزمنية وkeyboard، ثم بريدًا إداريًا حقيقيًا وكلمة مرور طويلة.
  4. اختر NIC الإدارة، hostname مثل pve01.corp.lab، IP 192.168.1.10/24، gateway 192.168.1.1 وDNS متاح مؤقتًا.
  5. بعد الإقلاع افتح https://192.168.1.10:8006 من شبكة موثوقة وسجل الدخول بـroot.
  6. اضبط NTP، افحص التخزين، وثبّت التحديثات من المستودع المناسب لترخيصك.
  7. فعّل MFA لحساب الإدارة، وأنشئ حساب مسؤول منفصل بدل الاستخدام اليومي لـroot.
pveversion -v
ip -br address
ip route
timedatectl
lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS
لا تنسخ أوامر مستودعات Proxmox من مدونات قديمة. اختر enterprise إذا عندك اشتراك، أو no-subscription حسب الدليل الرسمي الحالي؛ لا تفعّل المستودعين لنفس الحزم.
بوابة النجاح: واجهة Proxmox تعمل بعد reboot، وpveversion -v لا يعرض أخطاء حزم.
المرحلة 04

إنشاء Bridges والشبكة الافتراضية

vmbr0

External/OOB. يحمل إدارة Proxmox وpfSense WAN وNB-GW01.

vmbr1

Internal trunk بلا IP أو physical port، وVLAN-aware للزونز 10–60.

vmbr2

Monitor bridge بلا IP، يوصل نسخة الترافيك إلى Sniff NIC في SO01.

استخدم واجهة Proxmox: Node → System → Network → Create → Linux Bridge. المثال التالي مرجعي؛ استبدل eno1 باسم NIC الحقيقي من ip -br link.

auto lo
iface lo inet loopback

iface eno1 inet manual

auto vmbr0
iface vmbr0 inet static
    address 192.168.1.10/24
    gateway 192.168.1.1
    bridge-ports eno1
    bridge-stp off
    bridge-fd 0

auto vmbr1
iface vmbr1 inet manual
    bridge-ports none
    bridge-stp off
    bridge-fd 0
    bridge-vlan-aware yes
    bridge-vids 10 20 30 40 50 60

auto vmbr2
iface vmbr2 inet manual
    bridge-ports none
    bridge-stp off
    bridge-fd 0
طبّق التغيير من Console المحلي. لا تستخدم ifreload -a عن بعد إذا لم تكن لديك وسيلة استعادة.
بوابة النجاح: Proxmox ما زال متاحًا على 192.168.1.10، وvmbr1/vmbr2 لا يحملان IP أو gateway.

  1. أنشئ VM وثبّت pfSense، ثم أزل ISO بعد أول reboot.
  2. من Console عيّن vtnet0 كـWAN وvtnet1 كـLAN/trunk. لا تنشئ VLANs في شاشة التعيين الأولى إذا ستكمل من Web UI.
  3. اضبط WAN على 192.168.1.2/24 والبوابة 192.168.1.1. بما أن WAN شبكة خاصة، ألغِ Block private networks لهذه الواجهة فقط.

  5. افتح Web UI وشغّل Wizard، غيّر admin password، NTP وDNS.
  6. من System → Advanced → Networking تحقق من تعطيل Hardware Checksum Offloading مع VirtIO، ثم reboot.
  7. اترك NAT التلقائي في البداية، ولا تفتح أي Port Forward للوحات الإدارة.
بوابة النجاح: من VM مؤقتة على VLAN 10 تستطيع فتح pfSense، وpfSense يستطيع ping للبوابة والإنترنت.
المرحلة 06

إنشاء VLANs وDHCP وسياسات الجدار

  1. اذهب إلى Interfaces → Assignments → VLANs وأنشئ VLAN 10/20/30/40/50/60 على parent vtnet1.
  2. عيّن كل VLAN كواجهة، فعّلها، وسمّها MGMT/USERS/SERVERS/SOC/DMZ/ATTACK.
  3. استخدم gateways: 10.10.X.1/24. لا تضع upstream gateway على الواجهات الداخلية.
  4. فعّل DHCP فقط على USERS من 10.10.20.100–200 وعلى ATTACK من 10.10.60.100–150. الخوادم static.
  5. أنشئ aliases: DC01، SOC_SERVERS، DMZ_SERVERS، MGMT_PORTS.
  6. ابنِ القواعد من الأكثر تحديدًا للأقل، وفعّل logging على deny rules.

المرحلة 08

Windows Server 2022 وWindows 11

DC01 — تثبيت الدومين

  1. ثبّت Windows Server 2022 Desktop Experience مع Windows ISO وVirtIO ISO موصولين.
  2. إذا لم يظهر القرص، اختر Load Driver وحدد تعريف vioscsi x64؛ بعد الدخول ثبّت VirtIO Guest Tools.
  3. ضع IP 10.10.30.10/24، gateway 10.10.30.1، وDNS مؤقتًا 127.0.0.1 بعد تثبيت DNS.
  4. غيّر الاسم إلى DC01 ثم ثبّت AD DS وأنشئ forest باسم corp.lab وNetBIOS باسم CORP.
  5. أنشئ OUs: Servers, Workstations, Users, Admins, Service Accounts، ثم حساب مستخدم عادي وحساب إداري منفصل.
  6. اضبط DNS forwarders، الوقت، Advanced Audit Policy، PowerShell logging وWindows Defender.
# PowerShell كمسؤول على DC01
Rename-Computer -NewName "DC01" -Restart

# بعد إعادة التشغيل
Install-WindowsFeature AD-Domain-Services -IncludeManagementTools
Install-ADDSForest -DomainName "corp.lab" -DomainNetbiosName "CORP" -InstallDNS

CLIENT01 — الانضمام للدومين

  1. أنشئ Windows 11 VM بنمط UEFI/q35 مع EFI disk وTPM 2.0، واختر Windows 11 Pro.
  2. ثبّت VirtIO tools وQEMU Agent، وعيّن IP 10.10.20.10/24، gateway 10.10.20.1، DNS الوحيد 10.10.30.10.
  3. تحقق من nslookup corp.lab ثم انضم للدومين وأعد التشغيل.
  4. سجل الدخول بحساب CORP عادي وتحقق من تطبيق GPO.
Resolve-DnsName corp.lab -Server 10.10.30.10
Add-Computer -DomainName "corp.lab" -Credential "CORP\Administrator" -Restart

# بعد العودة
gpupdate /force
gpresult /r
nltest /dsgetdc:corp.lab
بوابة النجاح: مستخدم CORP يسجل الدخول إلى CLIENT01، وnltest يجد DC01 بدون استخدام DNS خارجي.

المرحلة 10

تثبيت Wazuh وربط الأجهزة

  1. ثبت Ubuntu 24.04 على WAZUH01 بعنوان 10.10.40.10، وطبّق baseline.
  2. نفّذ current Wazuh all-in-one assistant واحفظ credentials الناتجة خارج السيرفر.
  3. افتح Dashboard من MGMT فقط على https://10.10.40.10.
  4. من Dashboard اختر Deploy new agent وانسخ الأمر الذي يولده إصدارك لكل Windows/Linux host.
  5. أنشئ groups: Windows-Servers, Windows-Clients, Linux-Servers, DMZ، ثم تحقق من agent status.
  6. فعّل FIM وSCA وvulnerability detection تدريجيًا؛ لا تغيّر كل السياسات دفعة واحدة.
  7. بعد ثبات النسخة، عطّل repository التلقائي كما يوصي Quickstart لتجنب ترقية غير مقصودة، وخطط للترقيات.
curl -sO https://packages.wazuh.com/4.14/wazuh-install.sh
sudo bash ./wazuh-install.sh -a

# عرض كلمات المرور التي ولّدها المثبت
sudo tar -O -xvf wazuh-install-files.tar wazuh-install-files/wazuh-passwords.txt
أمر 4.14 مطابق للـQuickstart وقت إعداد هذا الدليل. قبل التنفيذ راجع الرابط الرسمي؛ إذا تغيّر الإصدار استخدم أمر الصفحة الحالية ولا تغيّر الرقم عشوائيًا.
استقبال Syslog من pfSense

أضف listener داخل /var/ossec/etc/ossec.conf ثم أرسل من pfSense: Status → System Logs → Settings → Remote Logging. اسمح UDP 514 من عنوان pfSense فقط.

<remote>
  <connection>syslog</connection>
  <port>514</port>
  <protocol>udp</protocol>
  <allowed-ips>192.168.1.2/32</allowed-ips>
</remote>

بعد النسخ الاحتياطي والتحقق من XML: sudo systemctl restart wazuh-manager.

بوابة النجاح: اختبار تغيير ملف على WEB01 ومحاولة تسجيل دخول فاشلة على CLIENT01 ينتجان أحداثًا قابلة للبحث.
المرحلة 11

Security Onion والرؤية الشبكية

  1. أنشئ SO01 بـCPU type host، 24 GB RAM، 300 GB disk وNICين: الإدارة على vmbr1 tag 40، والالتقاط على vmbr2 بلا tag.
  2. أقلع ISO واتبع المثبت الرسمي واختر Standalone للمختبر.
  3. عيّن management IP = 10.10.40.20/24، gateway 10.10.40.1 وDNS 10.10.30.10.
  4. حدد NIC الثانية كـmonitor/sniff فقط: لا IP ولا gateway.
  5. اسمح بإدارة Security Onion من MGMT/NetBird فقط.
  6. ابدأ بمصدر mirror واحد: واجهة pfSense الداخلية. بعد نجاحها أضف east-west sources عند الحاجة.
  7. افحص Capture Loss وZeek Loss والتخزين يوميًا في البداية.
لا تستخدم أسماء tap تخمينية. أسماء واجهات Proxmox تُنشأ من VMID وNIC وتتغير عند تعديل العتاد. استخرجها بعد تشغيل FW01 وSO01، ثم طبّق mirroring وفق توثيق Security Onion/Proxmox. في بيئة إنتاج استخدم physical TAP أو switch SPAN.
# على Proxmox: جمع معلومات فقط، بدون تغيير
qm config 100 | grep '^net'
qm config 150 | grep '^net'
bridge link | grep -E 'tap100|tap150|fwbr|vmbr2'

# داخل SO01: تحقق أن sniff NIC بلا IP
ip -br address
sudo tcpdump -ni <SNIFF_INTERFACE> -c 20
بوابة النجاح: افتح WEB01 من CLIENT01 ثم ابحث في Security Onion عن 10.10.20.10 و10.10.50.10 وترى الاتصال.
المرحلة 12

OpenCTI على CTI01

  1. جهز CTI01: Ubuntu 24.04، 8 vCPU، 24 GB RAM، 250 GB، IP 10.10.40.40.
  2. ثبّت Docker Engine وCompose plugin من مستودع Docker الرسمي، وليس حزمة عشوائية.
  3. استنسخ مستودع OpenCTI Docker الرسمي وانسخ .env.sample إلى .env.
  4. غيّر كل password، وأنشئ UUIDv4 صحيحًا لـadmin token وكل connector ID، وأنشئ encryption key طويل.
  5. طبّق vm.max_map_count=1048575 بشكل دائم.
  6. شغّل stack، راقب health وlogs، ولا تفعّل connectors كثيرة قبل ثبات الـcore.
  7. أضف MITRE ATT&CK connector أولًا، ثم مصدر CTI موثوق واحد، ولكل connector token مستقل.
  8. اقصر UI/API على SOC/MGMT أو NetBird، ثم ضع reverse proxy داخليًا مع TLS.
sudo sysctl -w vm.max_map_count=1048575
echo 'vm.max_map_count=1048575' | sudo tee /etc/sysctl.d/99-opencti.conf

git clone https://github.com/OpenCTI-Platform/docker.git ~/opencti-docker
cd ~/opencti-docker
cp .env.sample .env

# أنشئ القيم ولا تطبع ملف .env في التوثيق
uuidgen
openssl rand -base64 32

# بعد تحرير .env وتغيير كل القيم الافتراضية
sudo docker compose config
sudo docker compose up -d
sudo docker compose ps
sudo docker compose logs --tail=100
لا تستخدم changeme أو admin token مشترك. لا ترفع .env إلى GitHub. ثبّت إصدار image محدد بعد نجاح التجربة وقبل الاعتماد.
بوابة النجاح: تدخل إلى UI، ترى worker/connector healthy، وتستخرج API token محدود الصلاحية لاستخدام n8n.
المرحلة 13

n8n كطبقة SOAR

  1. جهز SOAR01 بعنوان 10.10.40.30 وثبّت Docker/Compose من المصدر الرسمي.
  2. ابدأ بقاعدة SQLite للمختبر فقط مع volume دائم؛ استخدم PostgreSQL إذا ستشغل workflows مستمرة أو متعددة المستخدمين.
  3. أنشئ encryption key قويًا، واضبط timezone = Asia/Riyadh، ولا تضع tokens داخل workflow JSON.
  4. اقصر 5678 على MGMT مؤقتًا، ثم استخدم TLS reverse proxy قبل الوصول عبر NetBird.
  5. أنشئ credentials منفصلة لـWazuh وOpenCTI والإشعارات بأقل صلاحية.
  6. ابنِ أول workflow: Webhook Test → Normalize JSON → OpenCTI HTTP Request → IF confidence → Notification → Manual approval.
  7. لا تجعل block/isolate تلقائيًا في البداية. الاستجابة الحساسة تحتاج approval وrollback.

NetBird للوصول الآمن

التصميم يستخدم NetBird Cloud في البداية وNB-GW01 كـrouting peer. لا نفتح Proxmox أو Wazuh أو OpenCTI أو n8n للإنترنت.

  1. جهز NB-GW01 على vmbr0 بعنوان 192.168.1.20/24، gateway 192.168.1.1.
  2. ثبّت NetBird client وسجله باستخدام setup key مخصص قصير الصلاحية، ثم احذف/عطل المفتاح.
  3. أضف static route على NB-GW01 إلى 10.10.0.0/16 عبر pfSense WAN 192.168.1.2.
  4. في NetBird أنشئ Network باسم SOC-LAB وحدد NB-GW01 كـrouting peer.
  5. أضف الموارد كعناوين /32: Proxmox .10، Wazuh 10.10.40.10، SO .20، n8n .30، OpenCTI .40، DC01 .10. تجنب 10.10.0.0/16 للمستخدمين.
  6. أنشئ مجموعة SOC-Admins وسياسات ports محددة. فعّل MFA/SSO وسجل activity.
  7. اختبر من لابتوب على شبكة جوال، ثم اختبر مستخدمًا غير مصرح وتأكد أنه مرفوض.
curl -fsSL https://pkgs.netbird.io/install.sh | sh

read -rsp "NetBird setup key: " NETBIRD_SETUP_KEY
sudo netbird up --setup-key "$NETBIRD_SETUP_KEY"

sudo ip route add 10.10.0.0/16 via 192.168.1.2
netbird status

اجعل route دائمة عبر Netplan بعد نجاح الاختبار. NetBird masquerade الافتراضي يبسط return path؛ إذا عطّلته ستحتاج return route صريحة وسيظهر source IP الحقيقي.

بوابة النجاح: SOC-Admins يصلون للواجهات المطلوبة فقط، ومجموعة أخرى لا تصل إليها.

ربط مسار التنبيه والإثراء والاستجابة

Detect

Wazuh للأجهزة وSecurity Onion للشبكة وpfSense للسياسات.

Enrich

n8n يستخرج IP/domain/hash ويستعلم OpenCTI بسياق وثقة ومصدر.

Respond

Ticket/notification أولًا، ثم approval، ثم block/isolate محدود مع rollback.

  1. وحّد schema داخل n8n: timestamp, source, host, user, rule_id, severity, observable_type, observable_value.
  2. استخدم Wazuh API account للقراءة فقط أو webhook integration مراجع للإصدار. لا تستخدم admin.
  3. في OpenCTI أنشئ service account/token مخصصًا لـn8n بقراءة indicators/observables.
  4. في n8n استخدم HTTP Request إلى http://10.10.40.40:8080/graphql داخليًا، Header من credential store، وquery مختبرة من OpenCTI API playground.
  5. إذا لم يوجد IOC، أكمل الحادث بدون enrichment بدل إسقاط التنبيه.
  6. إذا confidence عالٍ ومصدر موثوق، أنشئ ticket واطلب موافقة. لا تكتب كل alert تلقائيًا إلى OpenCTI.
  7. سجّل decision وanalyst ووقت التنفيذ ونتيجة rollback في كل workflow.
بوابة النجاح: alert تجريبي يصل n8n، يستعلم OpenCTI، ينشئ إشعارًا، ولا ينفذ حظرًا دون موافقة.

التقوية والنسخ الاحتياطي

Hardening

  • MFA على Proxmox وNetBird والحسابات الحساسة.
  • حسابات إدارية منفصلة وRBAC.
  • لا Port Forward للوحات الإدارة.
  • Default deny بين الزونز.
  • Pin للإصدارات وخطة تحديث شهرية.
  • حذف setup keys والتوكنات غير المستخدمة.

Backups

  • Proxmox configs وVM backups.
  • DC01 System State.
  • Wazuh custom rules/configuration.
  • OpenCTI volumes + Compose + encrypted secrets record.
  • n8n workflows/credentials/volume.
  • pfSense config.xml مشفر.
  1. أنشئ backup schedule منفصلًا عن snapshots.
  2. احتفظ بنسخة خارج السيرفر، مشفرة، مع retention واضح.
  3. اختبر restore لـVM صغيرة أولًا، ثم service-level restore لـn8n/OpenCTI.
  4. وثق RPO/RTO للمختبر ومن يملك مفاتيح الاستعادة.
بوابة النجاح: تستطيع استعادة خدمة واحدة وبياناتها بدون الاعتماد على snapshot حي.
