on Proxmox VE

An architecture and implementation guide for building a virtual company on one physical server. pfSense provides routing and policy enforcement; Windows Server provides identity and DNS; Wazuh monitors endpoints; Security Onion monitors network traffic; OpenCTI manages threat intelligence; n8n automates response; and NetBird provides remote access without publishing management dashboards to the Internet.

Assumptions and Design Boundaries

These values are a practical starting point. Adjust them after confirming the physical server specifications, NIC count, storage layout, and expected event volume.

Virtualization platform
Proxmox VE

One x86-64 KVM/QEMU node. A single node does not provide true high availability.

Remote access
NetBird Cloud

Managed control plane with an on-site Linux routing peer. Self-hosting is an optional later phase.

Security Onion mode
Standalone

Suitable for a lab or proof of concept: manager, search services, and sensor on one two-NIC VM.

    Proxmox VE Setup

    The host should provide virtualization only. Do not install SOC applications, Docker workloads, or offensive tools directly on Proxmox.

    vmbr0 · External/OOB

    Connected to the physical NIC. Carries Proxmox management, pfSense WAN, and the NetBird gateway.

    vmbr1 · Internal Lab

    VLAN-aware internal bridge with no IP, gateway, or physical port. Carries all virtual company networks.

    vmbr2 · Monitor

    No-IP bridge used only to deliver mirrored packets to Security Onion's second NIC.

    Do not paste network settings blindly. Replace the physical NIC name, management IP, and gateway. Work from local console or IPMI to avoid locking yourself out.
    Example /etc/network/interfaces

    Replace eno1 and 192.168.1.x. Use ip -br link to identify the real interface.

    Standard VM settings
    • Use q35 for modern guests and OVMF (UEFI) where required.
    • Use VirtIO SCSI Single, Discard, and IO Thread where storage supports them.
    • Use the VirtIO (paravirtualized) NIC model.
    • Install QEMU Guest Agent in Windows, Ubuntu, and Kali; do not assume support inside Security Onion without checking its guidance.
    • Windows 11 requires an EFI disk and virtual TPM 2.0.
    • Security Onion requires CPU type host and at least two NICs.

    Generic VM creation procedure
    1. Select the node, choose Create VM, and assign the VMID and hostname from the resource table.
    2. Select the correct ISO and guest type; verify BIOS and machine type before installation.
    3. Allocate CPU, RAM, and disk according to the plan and place high-I/O systems on SSD/NVMe.
    4. Select the correct bridge and VLAN tag. The pfSense trunk and Security Onion sniff NIC are documented exceptions.
    5. Install updates, QEMU Guest Agent, NTP, and static IPs for servers.
    6. Create a clean-baseline snapshot after initial configuration, while maintaining a separate real backup.

    Network creation order
    1. Create vmbr1 as a VLAN-aware bridge with no IP.
    2. Attach pfSense net1 to vmbr1 without a Proxmox VLAN tag because it is the trunk.
    3. Inside pfSense, create VLANs 10, 20, 30, 40, 50, and 60 on the LAN/trunk parent.
    4. Assign every VLAN as an interface with gateway 10.10.X.1/24.
    5. For each ordinary VM NIC, select vmbr1 and set the correct VLAN tag.
    6. Verify gateway reachability, DNS, and policy behavior before installing agents or applications.

    Recommended routing-peer setup
    1. Create Ubuntu VM NB-GW01 on vmbr0 with static address 192.168.1.20/24.
    2. Install NetBird and enroll it using a setup key assigned to the routing-peers group.
    3. Add a route on NB-GW01 for 10.10.0.0/16 through pfSense WAN 192.168.1.2.
    4. Create separate NetBird Network Resources for every required /32 or subnet and attach them to this routing peer.
    5. Leave masquerade enabled in the lab to avoid adding overlay return routes to internal systems.
    6. On pfSense, permit 192.168.1.20 only to approved resources and ports, then block everything else.

    Optional later self-hosting

    Place a separate VM in the DMZ with a public domain and TLS. Current NetBird guidance calls for at least 1 CPU and 2 GB RAM, with public TCP 80/443 and UDP 3478. Self-hosting adds update, backup, certificate, and relay responsibility, so Cloud is simpler for the initial lab.

    Windows Server and Active Directory

    DC01 provides company identity and DNS. CLIENT01 represents an employee endpoint joined to the domain.

    DC01 · 10.10.30.10

    Windows Server 2022 Standard Evaluation (Desktop Experience), proposed domain corp.lab, roles AD DS and DNS.

    CLIENT01 · 10.10.20.10

    Windows 11 Pro, DNS 10.10.30.10, joined to corp.lab, with Sysmon and Wazuh Agent.

    Domain build order
    1. Assign DC01 a static IP, set its hostname, and verify time synchronization.
    2. Install AD DS and DNS, then create a new corp.lab forest.
    3. Create OUs for Users, Workstations, Servers, Admins, and Service Accounts.
    4. Create separate test identities: standard user, helpdesk, SOC analyst, and emergency-only Domain Admin.
    5. Point CLIENT01 DNS to DC01, join the domain, and move the computer to the correct OU.
    6. Enable Advanced Audit Policy, PowerShell logging, and command-line capture for process creation.
    7. Install Sysmon with a reviewed configuration and verify events arrive in Wazuh.
    Install Windows with VirtIO
    1. Attach the Windows ISO as the first CD/DVD and virtio-win.iso as the second.
    2. Use VirtIO SCSI Single and a VirtIO NIC.
    3. If no disk appears, choose Load driver and select the matching x64 vioscsi driver.
    4. After first login, install VirtIO Guest Tools for networking, QEMU Guest Agent, and remaining drivers.
    5. Enable QEMU Guest Agent in Proxmox options after installing it inside Windows.
    6. For Windows 11, use UEFI, an EFI disk, TPM 2.0, and select Pro from the multi-edition ISO.
    Recommended monitoring and hardening GPOs
    • Audit Logon/Logoff, Account Logon, Account Management, Directory Service Access, Policy Change, Privilege Use, and Process Creation.
    • Enable PowerShell Module Logging, Script Block Logging, and lab transcription.
    • Keep Windows Defender and Firewall enabled; do not disable controls merely to simplify exercises.
    • Disable Guest, reject weak passwords, configure reasonable lockout, and separate administrator accounts from daily-use accounts.
    • Enable Windows LAPS when adding multiple endpoints.

    Security Onion NDR/NSM

    SO01 analyzes mirrored packets with Suricata, Zeek, and full packet capture for network-centric investigation.

    Management NIC

    vmbr1 tag 40, static IP 10.10.40.20, gateway 10.10.40.1.

    Sniff NIC

    vmbr2, no IP, no gateway, receives mirrored traffic only.

    Standalone minimum

    4 CPU, 24 GB RAM, 200 GB disk, and 2 NICs; this plan assigns 300 GB.

    Security Onion settings in Proxmox
    • Set CPU type to host.
    • Add a dedicated second capture NIC with no IP address.
    • Best packet source: physical NIC passthrough from TAP/SPAN. A mirrored virtual NIC is acceptable for the lab.
    • Disable NIC offloading on the capture interface/bridge as directed by official documentation to preserve packet visibility.
    • On Proxmox 9 or later, the sniffing path may require MTU 9000 depending on the current Security Onion guidance and environment.
    • Monitor Capture Loss and Zeek Loss after traffic begins.
    Lab mirroring strategy

    Phase 1: mirror ingress and egress on pfSense's internal interface to the sniff NIC. This covers traffic crossing the firewall between VLANs and the Internet.

    Phase 2: when a VLAN contains multiple hosts, mirror their tap interfaces as well to observe east-west traffic that does not cross pfSense.

    Production: use a dedicated TAP or SPAN source, preferably inside the NAT boundary so original host addresses remain visible.

    Do not run tc commands with guessed tap names. Identify real interfaces after creating the VMs, then create a systemd service that restores rules after reboot or VM changes.

    Connectors and SOC integration
    • Begin with MITRE ATT&CK and the official import/export connectors, then add trusted CTI sources one at a time.
    • Create a separate user and token for each connector with the Connector role; never share the admin token between services.
    • n8n receives a Wazuh or Security Onion alert, extracts IP/domain/hash, queries the OpenCTI GraphQL API, and adds context to the incident.
    • n8n may create a Sighting, Case, or Note after validation. Do not automatically promote every alert into knowledge.
    • Do not assume a native bidirectional Wazuh ↔ OpenCTI integration for every use case. Use n8n/API or a supported, version-reviewed connector.
    • Use marking definitions, confidence, labels, source reliability, retention, and indicator decay to prevent stale IOCs remaining active forever.
    Backup and security
    • Back up Docker Compose, the encrypted environment file, and OpenSearch, MinIO, Redis, and RabbitMQ volumes.
    • Do not rely only on copying live volume files; use a consistent backup procedure and test restoration on a separate VM.
    • Use RBAC and MFA/SSO where available, protect a break-glass account, and track every API token, owner, and rotation date.
    • Monitor disk usage, index health, RabbitMQ queues, worker errors, and connector last-run status.

    Recommended first workflow
    1. A webhook receives a High or Critical Wazuh alert.
    2. Validate the schema and reject unsigned requests.
    3. Extract source IP, agent name, rule ID, and MITRE technique.
    4. Retrieve asset context, then query OpenCTI GraphQL for the IOC, relationships, confidence, and source.
    5. Create a consistently titled incident containing evidence and links.
    6. Notify the analyst and request blocking approval.
    7. Only after approval, invoke Wazuh Active Response or a secured pfSense API/SSH action.
    8. Record the approver, action time, result, and rollback procedure.

    Hardening, Secrets, and Backup

    These controls prevent the lab from becoming an entry point into the real environment.

    Identity

    • MFA on Proxmox and NetBird
    • Separate admin identities
    • Least privilege
    • No shared accounts

    Network

    • No management port forwarding
    • Default deny between VLANs
    • Narrow NetBird resources
    • Isolated Kali

    Secrets

    • Password manager
    • Rotate API keys
    • No secrets in Git/workflows
    • Encrypted backup

    Updates

    • Maintenance window
    • Temporary pre-update snapshot
    • Read release notes
    • Document rollback

    Backups

    • Proxmox configuration
    • VM backups
    • Wazuh custom rules
    • OpenCTI data/volumes
    • n8n workflows/credentials

    • Internal TLS
