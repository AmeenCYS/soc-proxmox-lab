اضغط على أي مكوّن

ستظهر هنا الوظيفة، الواجهات، الاعتماديات والنقاط الأمنية الخاصة بالمكوّن.

    إعداد Proxmox VE

    المضيف يدير الافتراضية فقط. لا تثبت عليه تطبيقات SOC أو Docker أو أدوات هجومية.

    vmbr0 · External/OOB

    مرتبط بكرت الشبكة الحقيقي. يحمل IP إدارة Proxmox، وpfSense WAN، وNetBird Gateway.

    vmbr1 · Internal Lab

    Bridge داخلي VLAN-aware بدون IP أو gateway أو physical port. يحمل جميع شبكات الشركة الافتراضية.

    vmbr2 · Monitor

    Bridge بلا IP مخصص لنسخ الحزم إلى واجهة Security Onion الثانية. لا يُستخدم للتصفح أو الإدارة.

    لا تنسخ إعداد الشبكة كما هو مباشرة. اسم الكرت الفعلي وIP الإدارة والـgateway تختلف عندك. اعمل من شاشة السيرفر المحلية أو IPMI حتى لا تقفل نفسك خارج Proxmox.
    نموذج /etc/network/interfaces

    بدّل eno1 و192.168.1.x بالقيم الفعلية. نفّذ ip -br link لمعرفة اسم الكرت.

    auto lo
iface lo inet loopback

iface eno1 inet manual

auto vmbr0
iface vmbr0 inet static
    address 192.168.1.10/24
    gateway 192.168.1.1
    bridge-ports eno1
    bridge-stp off
    bridge-fd 0

auto vmbr1
iface vmbr1 inet manual
    bridge-ports none
    bridge-stp off
    bridge-fd 0
    bridge-vlan-aware yes
    bridge-vids 2-4094

auto vmbr2
iface vmbr2 inet manual
    bridge-ports none
    bridge-stp off
    bridge-fd 0
    إعدادات VM القياسية
    • Machine type: q35 للأنظمة الحديثة، وBIOS: OVMF (UEFI) عند الحاجة.
    • Disk controller: VirtIO SCSI Single مع Discard وIO Thread عند دعم التخزين.
    • Network model: VirtIO (paravirtualized).
    • فعّل QEMU Guest Agent بعد تثبيته داخل Windows/Ubuntu/Kali. لا تعتمد عليه في Security Onion إلا وفق دعمه.
    • Windows 11 يحتاج EFI Disk وTPM 2.0 افتراضيًا.
    • Security Onion: CPU type = host وواجهتان على الأقل.
    ISO Storage وتسميات الملفات

    ارفع ملفات ISO إلى local → ISO Images، واستعمل أسماء واضحة مثل:

    windows-server-2022-eval-x64.iso
windows-11-pro-x64.iso
ubuntu-24.04-live-server-amd64.iso
kali-linux-installer-amd64.iso
securityonion-x86_64.iso
pfsense-amd64.iso
virtio-win.iso

    ملف VirtIO ليس نظام تشغيل؛ هو ISO تعريفات Windows المطلوبة ليظهر القرص والشبكة بأفضل أداء داخل Proxmox.

    خطوات إنشاء أي VM داخل Proxmox
    1. اختر العقدة ثم Create VM، واكتب VMID وhostname من جدول الموارد.
    2. اختر ISO الصحيح ونوع النظام. لا تبدأ التثبيت قبل مراجعة BIOS وMachine type.
    3. خصص CPU/RAM/Disk بحسب الجدول، واجعل التخزين على SSD/NVMe.
    4. اختر Bridge وVLAN Tag بدقة؛ pfSense trunk وSecurity Onion sniff استثناءان موضحان في الدليل.
    5. ثبّت النظام، ثم updates وQEMU Guest Agent وNTP وIP ثابت للخوادم.
    6. خذ Snapshot باسم clean-baseline بعد اكتمال الإعداد الأساسي، لكن احتفظ أيضًا بـBackup حقيقي.

    1. أنشئ vmbr1 واجعله VLAN-aware بدون IP.

    6. اختبر الوصول إلى gateway قبل تركيب أي Agent أو تطبيق.

    pfSense: التوجيه والحماية

    هو نقطة التحكم الوحيدة بين القطاعات. طبّق القواعد من الأكثر تحديدًا إلى الأقل، وضع Default Deny في النهاية.

    واجهات VM 100

    WAN: vmbr0، مثال 192.168.1.2/24، gateway 192.168.1.1.

    TRUNK: vmbr1 بلا Proxmox tag؛ VLANs تُنشأ داخل pfSense.

    خدمات أساسية

    إعداد Routing Peer المقترح
    1. أنشئ Ubuntu VM باسم NB-GW01 على vmbr0 بعنوان ثابت 192.168.1.20/24.
    2. ثبّت NetBird واربطه باستخدام Setup Key خاص بمجموعة routing-peers.
    3. أضف static route على NB-GW01: الشبكة 10.10.0.0/16 عبر pfSense WAN 192.168.1.2.
    4. في NetBird أنشئ Network Resources منفصلة لكل /32 أو subnet مطلوب، واربطها بالـRouting Peer.
    5. اترك Masquerade مفعّلًا في المختبر لتفادي إضافة return routes للـoverlay.
    6. في pfSense اسمح من 192.168.1.20 إلى الموارد والمنافذ فقط، ثم احظر الباقي.
    sudo ip route add 10.10.0.0/16 via 192.168.1.2
ip route get 10.10.40.10
netbird status

    إذا قررتم Self-hosted لاحقًا

    أضف VM منفصلة في DMZ مع public domain وTLS. بحسب متطلبات NetBird الرسمية الحالية تحتاج على الأقل 1 CPU و2 GB RAM، والوصول العام إلى TCP 80/443 وUDP 3478. هذا يزيد مسؤولية التحديث والنسخ الاحتياطي والـrelay، لذلك Cloud أبسط في البداية.

    Windows Server وActive Directory

    DC01 يوفر هوية الشركة وDNS. CLIENT01 يمثل جهاز موظف وينضم إلى الدومين.

    DC01 · 10.10.30.10

    Windows Server 2022 Standard Evaluation (Desktop Experience)، اسم الدومين المقترح corp.lab، والأدوار: AD DS وDNS.

    CLIENT01 · 10.10.20.10

    Windows 11 Pro، DNS = 10.10.30.10، منضم إلى corp.lab، عليه Sysmon وWazuh Agent.

    ترتيب إعداد الدومين
    1. ضع IP ثابتًا لـDC01، وغيّر hostname، واضبط الوقت.
    2. ثبّت AD DS وDNS ثم أنشئ Forest جديدًا باسم corp.lab.
    3. أنشئ OUs: Users وWorkstations وServers وAdmins وService Accounts.
    4. أنشئ حسابات اختبار منفصلة: مستخدم عادي، Helpdesk، SOC Analyst، Domain Admin للطوارئ فقط.
    5. وجّه DNS في CLIENT01 إلى DC01 ثم ضمه للدومين وانقله إلى OU المناسبة.
    6. فعّل Advanced Audit Policy وPowerShell logging وProcess Creation command line.
    7. ثبت Sysmon بملف إعداد معروف ومراجعته قبل الاستخدام، ثم تأكد من وصول Event Logs إلى Wazuh.
    تثبيت Windows على VirtIO في Proxmox
    1. اربط Windows ISO كـCD/DVD أول، واربط virtio-win.iso كـCD/DVD ثانٍ.
    2. اختر SCSI Controller = VirtIO SCSI Single وكرت الشبكة = VirtIO.
    3. إذا لم يظهر القرص أثناء Setup اضغط Load driver واختر تعريف vioscsi المطابق لـWindows 11 أو Server 2022 x64.
    4. بعد أول دخول شغّل مثبت VirtIO Guest Tools من ISO لتثبيت الشبكة وQEMU Guest Agent وبقية التعريفات.
    5. من Options في Proxmox فعّل QEMU Guest Agent بعد تثبيته داخل Windows.
    6. في Windows 11 استخدم UEFI وEFI Disk وأضف TPM 2.0؛ اختر Windows 11 Pro من الـmulti-edition ISO.
    GPOs المقترحة للرصد والتقوية
    • Audit Logon/Logoff، Account Logon، Account Management، Directory Service Access، Policy Change، Privilege Use، Process Creation.
    • PowerShell Module Logging وScript Block Logging وTranscription داخل المختبر.
    • Windows Defender وFirewall مفعّلان؛ لا تعطلهما لتسهيل السيناريوهات.
    • تعطيل Guest، منع كلمات المرور الضعيفة، Account Lockout منطقي، وفصل حساب الإدارة عن الاستخدام اليومي.
    • تفعيل Windows LAPS عند إضافة أكثر من endpoint لإدارة كلمات مرور المسؤول المحلي.

    • Ubuntu WEB01 وSOAR01 وNB-GW01: Wazuh Agent مع مراقبة auth، sudo، package inventory وFIM.
    • pfSense وProxmox: Syslog مركزي عند الحاجة بدل تثبيت مكونات غير ضرورية على الـhypervisor/firewall.
    • لا تثبت Wazuh Agent داخل Security Onion ما لم تكن قد راجعت تعارضاته وسياسة الدعم؛ راقبه من الخارج.
    سياسات الاحتفاظ والتنبيهات
    • ابدأ بـ30 يومًا في المختبر، ثم قِس معدل الأحداث وحجم الفهارس.
    • أنشئ تنبيهات High/Critical فقط إلى n8n في البداية حتى لا تغرق بالأحداث.
    • احفظ قواعدك المخصصة خارج مسارات الحزم، ووثّق rule ID والمنطق ومصدر البيانات.
    • اختبر كل rule بحدث معروف وسجل النتيجة المتوقعة والفعلية.

    Security Onion NDR/NSM

    SO01 يرى الحزم المنسوخة ويستخدم Suricata وZeek وFull Packet Capture للتحليل الشبكي.

    Management NIC

    vmbr1 tag 40، IP ثابت 10.10.40.20، gateway 10.10.40.1.

    Sniff NIC

    vmbr2، بلا IP وبلا gateway، تستقبل mirror فقط.

    Minimum Standalone

    4 CPU، 24 GB RAM، 200 GB disk و2 NICs؛ الخطة تخصص 300 GB.

    إعدادات Proxmox الخاصة بـSecurity Onion
    • CPU Type = host لتمرير خصائص المعالج المطلوبة.
    • أضف NIC ثانية مخصصة للالتقاط ولا تمنحها عنوان IP.
    • مصدر الحزم الأفضل: Physical NIC passthrough من TAP/SPAN. للمختبر يمكن استخدام Virtual NIC مع mirroring.
    • عطّل NIC offloading على الواجهة/bridge المستخدم للالتقاط وفق الدليل الرسمي حتى لا تتشوّه رؤية الحزم.
    • في Proxmox 9 أو أحدث قد تحتاج MTU 9000 على مسار sniffing بحسب توجيهات Security Onion وحالتك الفعلية.
    • راقب Capture Loss وZeek Loss بعد بدء الترافيك.
    استراتيجية mirroring داخل المختبر

    المرحلة الأولى: انسخ ingress وegress لواجهة pfSense الداخلية إلى Sniff NIC. هذا يغطي الترافيك الذي يعبر الـfirewall بين VLANs والإنترنت.

    المرحلة الثانية: إذا أصبح لديك أكثر من جهاز في VLAN واحدة، انسخ tap interfaces لتلك الأجهزة أيضًا حتى ترى east-west traffic الذي لا يمر عبر pfSense.

    الإنتاج: استخدم TAP أو SPAN مخصصًا، ويفضل التقاط الحركة داخل حد NAT لرؤية عناوين الأجهزة الحقيقية.

    لا تطبق أوامر tc بأسماء tap تخمينية. استخرج أسماء الواجهات الفعلية بعد إنشاء الـVMs، ثم ابنِ خدمة systemd تعيد القواعد بعد reboot أو تغيير VM.

    OpenCTI — منصة معلومات التهديدات

    CTI01 يحوّل مؤشرات الاختراق والمهاجمين والحملات والتقنيات إلى معرفة مترابطة بصيغة STIX 2.1، ويزوّد المحلل وn8n بسياق يساعد على اتخاذ القرار.

    VM
    165 · CTI01

    Ubuntu Server 24.04 على VLAN 40 بعنوان 10.10.40.40.

    Lab allocation
    8 vCPU · 24 GB

    250 GB SSD/NVMe كبداية مع مراقبة الاستهلاك ونمو الفهرس.

    UI / GraphQL API
    8080/TCP

    داخلي فقط؛ الأفضل تقديمه على 443 عبر reverse proxy وTLS.

    Data model
    STIX 2.1

    Indicators وObservables وThreat Actors وCampaigns وReports وRelationships.

    OpenCTI ليس ملف ISO مستقلًا. أنشئ له Ubuntu Server VM جديدة ثم ثبّت المنصة ومكوّناتها عبر Docker Compose الرسمي. لا تضعه مع n8n في نفس VM لأن OpenSearch وRabbitMQ وMinIO وRedis تحتاج موارد وعزلًا مستقلًا.
    المكونات والموارد

    الـstack الرسمي يعتمد على OpenCTI Core وWorkers وConnectors إضافة إلى OpenSearch/Elasticsearch وRedis وRabbitMQ وMinIO/S3. المتطلبات الرسمية الدنيا للمكونات مجتمعة مرتفعة؛ لذلك خُصصت للـVM في هذا المختبر 8 vCPU و24 GB RAM و250 GB SSD. هذا حجم مختبر، وليس sizing إنتاجي.

    المكوّنالدورالحد الرسمي المرجعيملاحظة المختبر
    OpenCTI CoreUI وGraphQL API2 cores و≥8 GB RAMStateless؛ يعمل ضمن Docker stack.
    OpenSearch/Elasticsearchالبحث والفهرسة2 cores و≥8 GB RAM وSSDأكبر مستهلك للذاكرة والقرص.
    RedisCache/coordination1 core و≥1 GB RAMVolume دائم ومراقبة health.
    RabbitMQMessage broker1 core و≥512 MB RAMيربط المنصة بالـworkers والـconnectors.

    Workers/Connectorsكتابة البيانات والاستيراد والإثراء1 core و≥128 MB لكل عملية كمرجعابدأ بعدد قليل وزِد حسب queue والتحميل.

    الـConnectors والتكامل مع SOC
    • ابدأ بموصل MITRE ATT&CK والـimport/export connectors الموجودة في الـcompose الرسمي، ثم أضف مصادر CTI موثوقة واحدة تلو الأخرى.
    • أنشئ مستخدمًا وToken منفصلًا لكل connector بصلاحية Connector فقط؛ لا تشارك admin token بين الخدمات.
    • n8n يستقبل alert من Wazuh أو Security Onion، يستخرج IP/domain/hash، ثم يستعلم GraphQL API في OpenCTI ويضيف enrichment إلى الـincident.
    • يمكن لـn8n إنشاء Sighting أو Case/Note في OpenCTI بعد التحقق، لكن لا ترفع كل Alert تلقائيًا حتى لا تلوث قاعدة المعرفة.
    • لا تفترض وجود تكامل Wazuh ↔ OpenCTI أصلي ومباشر لكل حالة. استخدم API/n8n أو connector مدعوم ومراجع للإصدار.
    • استخدم marking definitions وconfidence وlabels وsource reliability، وحدد retention وindicator decay لمنع بقاء IOCs قديمة فعالة بلا نهاية.
    النسخ الاحتياطي والحماية
    • انسخ Docker Compose وملف البيئة بعد تشفيره، وvolumes الخاصة بـOpenSearch وMinIO وRedis وRabbitMQ.
    • لا تعتمد على نسخ ملفات volume وهي نشطة فقط؛ استخدم إجراء backup متسق واختبر الاستعادة على VM منفصلة.
    • فعّل RBAC وMFA/SSO إن توفر، واحتفظ بحساب break-glass محمي، وسجل كل API token ومالكه وتاريخ تدويره.
    • راقب disk usage وindex health وRabbitMQ queues وworker errors وconnector last run.

    Workflow أول مقترح
    1. Webhook يستقبل Wazuh alert بمستوى High أو Critical.
    2. Validate schema ويمنع الطلبات غير الموقعة.
    3. يستخرج source IP وagent name وrule ID وMITRE technique.
    4. يجلب بيانات الأصل من جدول داخلي، ثم يستعلم OpenCTI GraphQL API عن الـIOC وعلاقاته ودرجة الثقة.
    5. ينشئ Incident بعنوان موحد ويضم الأدلة والروابط.
    6. يرسل إشعارًا للمحلل ويطلب Approval للحظر.
    7. بعد الموافقة فقط: يستدعي Wazuh Active Response أو API/SSH آمن إلى pfSense.
    8. يوثق من وافق، وقت الإجراء، والنتيجة، ويضع rollback step.
